# Audit, 2026-10-20 (read-only; nothing was fixed)

Scope: chat-pilot data and training path as of this date. No code, data, model or run directory was modified. Scratch scripts lived in the session scratchpad and are not in the repo.

**Tests:** `.venv\Scripts\python.exe -m pytest tests -m "not slow" -q` gave `74 passed, 1 deselected in 140.60s`. Passing tests do not cover any defect below. No test exercises `persona_rules.violations` with a system message, `bulk_review.approve` with a small sample, or the early-stopping and best-checkpoint paths.

**Not reviewed:** `review_sheets.py`, `train_prepared.py` beyond `load_split`, tokenizer/vocabulary migration, Kaggle scripts, `_legacy/`. Findings marked *suspicion* were reasoned from code and not reproduced.

## A. Confirmed defects (reproduced by running code or reading the artifact), most severe first

### A1. HIGH: persona filter skips the assistant turns when the first message is not `user` (`Tantra/data/persona_rules.py:31`)
`violations()` iterates `range(1, len(messages), 2)` and assumes strict `user, assistant, ...` alternation. `validate_record` accepts `system` messages and does not check alternation (`Tantra/data/expert_workbench.py:212-216`). `bulk_review.check` relies on `violations` (`bulk_review.py:43`).
- Failure: `[system, user "Hi", assistant "I'm an AI assistant from Atulya AI"]` returns `[]`. The reply is checked as if it were a user turn. The identical conversation without the system message returns two violations.
- Current impact: none. All 9,450 queue rows and all 508 v3 rows are strictly `user/assistant` alternating (roles tuples checked). It will bite as soon as a system-prompted or malformed batch enters the queue, and `bulk_review` would report `rejected: 0`.

### A2. HIGH: bulk approval has no minimum sample size and does not bind the sample to a draw (`Tantra/data/bulk_review.py:100-107`, `:77-81`)
`approve` only requires that every row in the CSV is Y/N and that the IDs are in the filtered batch. It does not check `n`, the seed, or that the CSV came from `draw_sample`.
- Failure: a CSV with one hand-picked easy row marked `Y` gives rate 100% and approves all 9,450 rows. A cherry-picked or re-drawn sample (another `--seed`) is indistinguishable from the default one.
- The written provenance is accurate about what was done (`sample_size`, `batch_size`, `decision_sha256`, reviewer string "spot-checked N of M"), so the fields are honest, but nothing enforces that the approval is meaningful. `review.status` is the same `reviewed` as row-by-row review, so downstream gates (`inspect`, `validate_record`) cannot tell them apart. Only the optional `review_method` field differs and no consumer reads it.
- The sample is not stratified. The pending `runs/conversation-bulk-v1/queue/spot-check.csv` has 50 rows covering 39 of 90 families: 41 smalltalk, 7 greeting, 1 farewell, 1 empathy. 51 families, each 105 rows, would have no reviewed member. Zero failures in 50 draws only bounds the true defect rate at about 6% (95% upper bound). Because the 9,450 rows are 90 families x 5 openers x 21 reply variants, a systematic defect in one family is likely to go unseen.
- The spot-check is still blank (0 of 50 marked) and the queue is `review_status: pending`; the status is correct today.

### A3. MEDIUM: `approve` can leave a partial export, and only sampled `N` rows are dropped (`bulk_review.py:113-119`)
The English-only check runs inside the write loop after `output.mkdir`. A non-English row mid-batch raises `ValueError` after earlier rows are written. A rerun then needs a new directory because `output.exists()` refuses (`:93`). Rows from the same family or template as a sampled `N` row stay approved.

### A4. MEDIUM: persona regexes are too loose to license mentions and too narrow to catch them (`persona_rules.py:8-17`)
Tested directly:
- `ASKS_CREATOR` contains very common words (`from`, `thank`, `make`, `life`, `world`, `story`, `mind`). `[user "I feel tired", assistant "I'm an AI, made by Atul Vij at Atulya AI"]` is flagged only for the creator mention; the unasked "I'm an AI" passes because `feel` is in `ASKS_AI`. Likewise a user turn containing "thank" (e.g. "thank you") licenses a creator mention (not run; "Thanks a lot" does not match `\bthank\b` and was flagged). A single early user question licenses every later assistant turn because `asked` joins all earlier user turns (`:22`).
- `SAYS_AI` / `SAYS_CREATOR` match only a few literal phrases. `[user "Hi", assistant "I'm a chatbot made by Atul."]` returns `[]` (no `an ai`, no `atul vij`).
- `SERVICE` bans the word "assistant" everywhere, including replies to "Are you an assistant?".
- Current impact: the queue has 0 assistant replies matching a broad `atul|atulya|ai|language model|bot|chatbot|software|virtual|program` pattern, and the v3 pilot rows have 0 violations under the current rules, so the existing data is clean. The rules are weak guards for future generators.

### A5. MEDIUM: split-leakage guard is tautological, and openers are not grouped (`Tantra/conversation_train.py:32-33`, `expert_workbench.py:414-438`)
`inspect` raises only if the same `split_group` appears in two splits. `prepare` already assigns split by `split_group`, so this can never trigger. Nothing groups rows by user opener or near-duplicate text: families are whatever `source.id:family_id` the drafting script chose, and only byte-identical `messages` are unioned.
Measured:
- v3 bundle (508 rows): 1 opener (`hi`) appears in both train and test (greeting vs identity_self). 0 val openers appear in train; 1 of 30 test rows has its opener in train. Cross-split token-Jaccard near-duplicates (>=0.7): 2 val rows, both spurious (very short strings), 0 test. v3 leakage is low.
- Queue vs v3, as the workbench would split the queue (family-level split gives families 77/7/6): 672 queue rows share an opener with a v3 row. Per split pair, in rows: queue-train/v3-train 609, queue-train/v3-test 42, queue-val/v3-train 21, queue-test/v3-train 21. If both are merged into one bundle by opener rather than family, 42 v3 test rows' openers appear in queue train, and 42 queue val/test rows' openers appear in v3 train, with different replies. The workbench has no check for this.
- Inside the queue: 0 openers span more than one family, and 0 cross-family, cross-split opener pairs at Jaccard >=0.8, so the queue's own split is clean.

### A6. MEDIUM: validation set too small to select a checkpoint or support claims (`conversation_train.py:116-130`, `:142-146`)
- v3: 19 val rows, 288 assistant targets (`runs/chat-en-pilot-local-v3/report.json`). Farewell has 1 val row, smalltalk 1, identity_capabilities 0 val/0 test, identity_limitations 0 val. Test is 30 rows.
- `best.pt` equals the final weights in v3 (`best_update` 918 = last update) while the same run's fresh-prompt answers regressed (documented in `CONVERSATION_TRAINING_STAGE.md:92-96`). Validation loss kept falling as the model memorised. v1 and v2 predate `best.pt` (`best_update: null`), so only their final weights exist.
- Val loss figures across v1/v2/v3 use different val sets (184/233/288 targets) and are not comparable; the docs say so for v2 only.
- `best.pt` stores no identity (bundle/base/tokenizer hashes, `:146`); `base.pt` is always the last weights (`:169`), not the best, and is named like the candidate base. `scripts/compare_chat_pilot.py` loads either with `strict=False` and no hash check.

### A7. MEDIUM: bulk queue composition will teach narrow behaviour (`runs/conversation-bulk-v1/queue/bulk-drafts.jsonl`)
Measured: 9,450 rows = 90 families x 105; 450 distinct first openers (each x21 replies); 809 distinct final replies overall. Smalltalk is 7,560 rows (80%) with 647 distinct replies; empathy is 315 rows with 27 distinct replies; farewell 420 rows with 36. Assistant turns ending in `?`: greeting 92%, empathy 79%, smalltalk 75%, farewell 54%; 60 farewell final replies end in a question. With the workbench split the queue would give empathy 0 val rows, farewell 0 val and 0 test rows, greeting 0 test rows.
This is a quality and evaluation risk, not a policy bug. It matches the stated goal of 10K+ conversations only in row count (about 450 independent situations).

### A8. MEDIUM: early stopping and best-checkpoint logic in the base pilot (`Tantra/data/train_base_pilot.py:98`, `:207-212`, `:224-226`)
- `best` starts at `inf` and the baseline evaluation is never compared. The first evaluation always becomes `best-base.pt`, even if worse than the starting weights.
- On `stopped_early`, `base.pt` holds the last (non-best) weights and the state is `stopped_early`. `conversation_train.train` accepts only `pilot_complete` (`conversation_train.py:92`), so an early-stopped base cannot be used for the chat stage without hand-copying `best-base.pt`. Nothing promotes the best weights.
- For the actual run, `runs/kaggle-output/base-training` finished `pilot_complete` with `bad_evals 0`; I confirmed `base.pt` and `best-base.pt` have the same SHA-256 (`673C701D...`), as HANDOFF says.

### A9. LOW: resume details (`train_base_pilot.py:217-223`, `:231-234`; `conversation_train.py:98`, `:131-137`)
- `metrics.jsonl` is appended every update but the checkpoint is written every 100 updates or 600 s. After a crash and resume, updates since the last checkpoint appear twice in the history.
- A `KeyboardInterrupt` between `optimizer.step()` and `cursor += ...` would checkpoint advanced weights with an old cursor, replaying one window on resume (narrow window).
- Resume rejects any change in `threads` (`:104`). A stale `training.lock` (crash) blocks resume with `FileExistsError` and needs manual deletion in both trainers.
- `conversation_train` resume restores optimizer, torch RNG, cursor and best. Order is regenerated from the fixed seed 42 and identity (bundle, base, tokenizer, mode, epochs) is checked, so resume looks correct. I did not run it.

### A10. LOW: base pilot data order (`train_base_pilot.py:29-35`)
`window_order` alternates hi/en and then runs the longer language alone once the shorter is exhausted, so "balanced" only holds for the shorter shard. Windows are in file order, not shuffled. Whether this skews anything depends on shard ordering; not measured.

## B. Verified OK (checked, no defect found)
- Assistant-only masking: `tokenizer.encode_chat` marks assistant body tokens plus `<|end|>` (role token masked), `encode_row` builds `-100` labels, and `loss` shifts labels (`tantra_model.py:340-343`). `conversation_train` rejects conversations over 256 tokens instead of truncating (`:108-110`). Per-token loss weighting across the 3-row microbatch is correct (`:153-159`). All assistant turns of multi-turn rows are supervised, as intended.
- `english_pilot` gate: never `data_ready`; `epochs>1` rejected outside the pilot; output must be separate from source; base language gate requires Hindi and English validation to beat baseline.
- v3 review fields: all 508 rows `status reviewed`, `fluent_language_review False`, `domain_review False`, source kind `original_ai_authored`, three owner-approval reviewer strings. No Hindi/Hinglish rows. `load_split` verifies split SHA-256 and re-runs `validate_record`.
- `compare_chat_pilot.py` `FRESH`/`PERSONA` prompts: none appear verbatim in v3 or the queue. They have been reused across v1-v3 comparisons, so treat them as a development set, not a held-out score.
- `bulk_review.load_queue` checks the queue file hash; `index.json` hash matches the drafts file as listed.

## C. Documentation claims not supported by code or recorded results
- `README.md:93` says adding experts "costs disk space, not CPU execution time". The engine loads all adapters into RAM at startup (`TantraModel.load`, `tantra_model.py:429-434`, used by `inference_engine.py:46`), which `HANDOFF.md:70-72` itself states. The README line is misleading for many experts.
- `README.md:37-38` (8,175 facts, 0.05 ms retrieval, ~0.24 s INT8 latency): no recorded run or doc in `docs/` or `runs/` contains these numbers. Unverified.
- `HANDOFF.md:19` (28.8M params, 10,277 tokens) describes the deployed `Model/`. The candidate trained base is d_model 512, 8 layers, 64K vocab (checked from `base.pt` config). The statement is scoped to `Model/` but easy to misread.
- `HANDOFF.md` and `CONVERSATION_TRAINING_STAGE.md` report pilot validation losses on 1-19 rows and conclusions such as "plateaued" from 12-22 hand-read prompts. They are labelled unvalidated, but the "plateau" and "regressed" conclusions rest on one greedy sample per prompt.
- Recorded numbers I did check and found consistent: Kaggle base final val (hi 2.642, en 5.699, 4,639 updates, 18,999,808 tokens), chat pilot v1 (6.85 to 3.05, 844 updates), v3 (7.06 to 3.14, 918 updates, best_update 918). `GREETING_PILOT.md` loss figures and "stopped at 620 and resumed" (v2) were not checked.

## D. CPU inference risks with many experts
Confirmed from code:
1. **Eager load:** `TantraModel.load` calls `add_expert` for every router name and loads every `experts/*.pt` (`tantra_model.py:426-434`). Measured sizes from the 64K base config (rank 8, targets q/v/o/down, 37,888 params per rank unit): rank 8 x 164 experts is about 190 MiB fp32. At the taxonomy target ranks (16 to 128) the 164 experts total 327,958,528 params, about 1,251 MiB fp32, plus the 218 MiB base. Load peak is higher because each file is deserialised before copying. Compute per token only scales with active experts (`LoRALinear.forward`), but `max_experts=2` routing means most loaded memory is idle.
2. **No adapter/base identity check:** `save_expert` stores only `{rank, state}` (`:442`). `load_expert_state` silently skips any key that is missing or has a different shape (`:299-300`). `load` uses `strict=False` for the base (`:428`). An adapter from the old 10K-vocab/28.8M base, or from a different pilot base, loads partially or as a no-op without any error. README says old adapters must be retrained, but the loader enforces nothing.
3. **Unsafe deserialisation:** `torch.load(..., weights_only=False)` on base and adapter files (`:423`, `:433`) executes arbitrary pickle code from any file placed in `Model/experts/`.

Suspicions (not reproduced):
- `quantize_for_cpu` replaces `mod.base` with a dynamic-quantized Linear, so `LoRALinear.weight` (returns `self.base.weight`) is no longer a tensor; `add_expert` after quantisation (uses `self.weight.device`) would fail.
- `TantraEngine.stream` stores active experts on the shared model (`set_active`) inside a generator; two interleaved streams would overwrite each other's routing.
- `train_base_pilot` checkpoints are saved from `model.state_dict()` on the training device. A CUDA run saves CUDA tensors; loaders that omit `map_location` would fail on CPU-only machines. The local copy of the Kaggle base loads on CPU with `map_location='cpu'`; `TantraModel.load` defaults to cpu, so the known paths are fine.
